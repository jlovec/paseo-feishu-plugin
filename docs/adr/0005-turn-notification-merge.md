# ADR 0005：会话完成通知的 30 秒合并窗口

状态：已确认（2026-11-09 实测）

## 背景

`agent.turn_ended` 每轮结束都会发一张完成卡片。一个 agent 连续追问或多轮执行时，
飞书里会连刷好几张内容相近的卡。需要在不丢信息的前提下减少消息条数。

## 结论

同一 agent 的连续 `completed` 通知按 **30 秒窗口**合并：

- 窗口**从第一张卡发出时开始计时**，合并期间不重新计时
- 窗口内再有完成 → `PATCH` 同一条消息，更新正文并追加「30 秒内合并 N 轮」
- 窗口结束后的第一次完成 → 新发一条卡，开启新窗口
- `failed` / `canceled` 不参与合并，独立发卡，并清掉该 agent 的合并状态

状态只存进程内存（agent id → messageId / windowStart / turns），插件重启后从零开始。

## 为什么从第一张卡开始计时

如果每次合并都重置窗口，只要 agent 每 30 秒内完成一次，就会无限更新同一条消息，
用户永远看不到一条新消息，也感知不到又有新的轮次。锚定第一张卡可以保证
**一个窗口最多占用一条消息、最多持续 30 秒**。

## 为什么不选其他方案

- **只通知需要关注的（完成不发）**：单人 P2P 通道里会丢掉主人本来想看的信息
- **完整列窗口内每一轮**：卡片会变长，且与「只关心最新状态」的诉求不符
- **等 30 秒静默再发第一张**：通知会延迟，失去实时性

## 实测

```
08:28:53  已发送会话通知：completed · 合并窗口测试2     ← 第一轮，新发
08:29:19  合并会话通知：合并窗口测试2 第 2 轮           ← 26.9 秒后，就地更新
```

飞书 API 回查：该 agent 全库只有 1 张卡，正文是第二轮的回复，
note 为「30 秒内合并 2 轮」。

## 影响

1. `server/notify.ts` 持有模块级 `Map<agentId, TurnMessage>`。
2. 合并走 `patchCard`；PATCH 失败时退回新发一条，通知不能丢。
3. 卡片底部在 `turns > 1` 时显示合并轮数（`server/cards.ts`）。
